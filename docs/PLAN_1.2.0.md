## 1. Rematch by pad inside the game

### Outcome and current behavior

Ship the promised 1.2.0 flow: after an authoritative result, show the result and available next actions over the game picture. The player accepts, declines, and starts the next available match using the pad in the game window. The launcher handles the lobby in the background. Keep the running game and connection when the existing server rules permit it. Include private rooms; preserve community-room rotation and ranked-set rules.

**Inference:** reusing the host overlay plus a local UI channel should remove the launcher-focus interruption without changing fight simulation. The code does not establish that the overlay, pad ownership and every post-result transition already work together; that needs a built game and repeated pair runs.

### Proposed design

1. **One host UI owner.** Add a small host-only menu state machine under `src/directfight` and compose its output with training through one overlay owner. Give a result/menu priority over training panels; hiding either layer must not clear the other. Reuse the renderer API from patch 0045, not guest UI memory. Display result, opponent vote/wait state, allowed actions, room/set context and remaining time. No new addresses are required by this design; any extra state/address not already documented here must first be established in the real project.

2. **A separate, versioned local UI subchannel.** Extend the control support in `df_ctl.cpp` and `match_driver.py`, but keep UI traffic separate from `cmd.json`'s fight/idle/quit sequence. Proposed files alongside the existing control files:

   | Direction | Proposed content and behavior |
   |---|---|
   | Launcher -> game, `ui.json` | `v`, launch generation, session identity, increasing UI revision, prompt ID, target match ID, room mode, prompt kind, localized display strings, allowed action IDs, remaining duration, acknowledgement of last action. Include a capability/ready exchange before suppressing launcher UI. |
   | Game -> launcher, `ui_action.json` | Same generation/session/prompt/match identities, increasing action sequence, selected action ID. Retain one pending action until acknowledged; retransmission has the same sequence. It is a local request, never a peer vote or fight command. |

   Write temp files then replace atomically; use shared-delete reads as existing control does. Keep sequence domains independent: current `ctl_poll()` advances `g_seen` for a parsed command, so an unrelated UI command could supersede an unconsumed fight/idle command. Use bounded parsing and bounded text/message sizes. Ignore malformed, old-version, stale-generation, wrong-session/match, expired, repeated or disallowed requests. Deduplicate before dispatch, including while an asynchronous client call is pending; return success/rejection in the acknowledgement. Do not overwrite an unacknowledged action with another one. New prompt/result revisions must not silently discard its acknowledgement.

   Perform file I/O on a host worker and exchange immutable snapshots with the live UI tick; no file polling, sleeps or network calls on the simulation/rollback path. Relative countdown display is advisory: the launcher/server remains authoritative on expiry. Restart, new match/session, disconnect and cancellation invalidate the old prompt. Process-mode games need the same explicit UI directory/capability, independent of `T5_CTL_DIR`; retain current fallback until that path is implemented and tested.

3. **Pad ownership and focus.** Sample the chosen local device through the existing local-pad layer once per live host tick; never execute menu actions during rollback re-simulation. Read raw local input for UI without modifying the simulation's pad stream or consuming its tap latch. Require the game to have focus for menu actions, require release after opening/focus return, then use button edges and one outstanding action until acknowledgement. Show mapped confirm/cancel hints; map accept/decline/next through action IDs, not text parsing. A held attack at KO must not accept a rematch or confirm a character. Keep gameplay inputs neutral under the existing post-match hold, and re-arm input before the next select. Pause/loss of focus changes host UI only.

4. **Reuse lobby authority.** The launcher translates a valid action into existing APIs: `MatchDriver.rematch(match, accept)` for a vote; `LobbyClient.ready()` for an actual ready check; room line/bar actions for community rooms (`client.py:1406-1438,1477,1536`). Add a context-specific next-match action for casual quick play through the existing queue path, once the previous decline/result cleanup completes. Do not queue publicly from a private room. Only a server `match_start` may cause `MatchDriver._start()` to send the next fight configuration. Keep result reporting, character choices, stage/rules, fixed time, connection negotiation and fresh-opponent reset in their existing paths.

   In a classic private room, accept uses the current match-ID rematch vote. Decline ends the offer but leaves room membership intact. A subsequent Next calls `LobbyClient.rematch()` **without a match ID** (`client.py:1477-1485`, `server/lobby.py:1795-1805`) to start the room's next ready check; `LobbyClient.ready()` responds only once that check exists. In a community private room, show rotation/countdown/waiting plus eligible ready, back-to-line or sit-out actions; never offer a rejected two-player rematch vote or bypass the waiting player. In a ranked set, show the automatic next-game countdown and the existing explicit leave-set semantics; decline must not accidentally become a forfeit. Tournament/expired/unavailable rematch states get only server-permitted actions.

   The current server requires recent-match participation, suitable idle/room state, no active rated set, no block and mutual votes; connection reuse also requires both `keep` votes and the existing path/no-swap restrictions (`server/lobby.py:1807-1853`). Do not duplicate or weaken these checks in the overlay. If more eligibility detail is needed for rendering, add optional server action metadata with old-client fallback.

5. **Keep the launcher behind after capability acknowledgement.** Adjust `_come_forward` call sites in `tk_tab.py` for supported in-game prompts and ranked-set completion. Continue background polling and result reporting. Current `MatchDriver.rematch(..., accept=False)` stops a process-mode game (`match_driver.py:874-875`); change that lifecycle for capable games so declining preserves a usable in-game idle/next menu, ending the old session safely before a new opponent. Until supported, use explicit launcher fallback for process mode rather than claiming pad-only Next works there. Preserve launcher fallback for old games, disabled/broken overlay, acknowledgement timeout, crash, manual-result recovery and explicit user return to launcher. Do not move focus on ordinary result/vote/ready updates. Add all new launcher/lobby strings to `i18n.py` and every `i18n_*.py` language catalog. The game receives translated strings from the launcher. Extend overlay font/glyph support for those languages, including Japanese/Korean; catalog completeness alone does not make the current bitmap font render them. Validate wrapping, long names, scaling and button hints.

### Optional casual default and automatic skips

**Casual rematch by default:** make this a separate product option, after explicit pad voting works. Selecting Rematch by default is the smallest change; automatic acceptance needs a visible cancellable countdown, disabled on decline/disconnect and evaluated only where `rematch_window` is offered. Prefer opt-in for automatic acceptance. Existing `auto_rematch` is a finite counter (`match_driver.py:850-869`), not a room-aware default policy. Add a separate preference rather than silently making that counter unlimited. Each client still sends its own vote; the server waits for both. Never apply this to ranked-set leave behavior, tournament matches or community rotation. If cancellation is allowed until countdown end, defer sending the accept until then: the current per-match dedupe does not provide vote retraction.

**Auto-skip replays/round-end parts:** distinguish what already exists from the option:

- `src/directfight/df_fight.cpp:527-539` already skips post-match presentation from 40 frames after the decision with START every 20 frames (`T5_DF_SKIP=0` disables it). Preserve its agreement with the netplay post-match path.
- `src/netplay/no_pause.h:1-43,54-66,109-157` defines the safe rule: mutual START during intros (round states 1/2) and nonfinal KO slow motion/replay/transition (8/9/0xC); once both have pressed, generate symmetric three-frame START pulses every 20 frames. Post-match START is allowed only after `kDelay=40` from a decision belonging to this fight, until select is requested. Fighting stays unpausable. Slow motion is a voting part even where START itself has no effect.
- Proposal: add an agreed match-level `auto_skip_after_round` flag, default off, through lobby fight config, direct-fight parsing and the existing match-rule distribution/replay metadata paths. Apply it **inside the deterministic rule**, treating both votes as present upon entry to an eligible after-round part; retain pulse cadence, history tags, rollback reconstruction and state guards. Keep intro skipping as a distinct option if desired. Do not add a local timer or inject raw START from the menu. Final-match skips continue under the existing delayed decision rule, not a new round-state shortcut.
- Audit `src/netplay/t5_hooks.cpp:623-676,1738,1829,2055` and `src/netplay/match_rules.h:1-43,54-81`: latch the same agreed flag at FIGHT START before netplay starts, fixed for the whole fight, and use it for live, re-simulated, spectator and replay frames. Include the flag in rule packing/unpacking, `any()` and equality. Edit anchors for propagation: `match_driver.py:372-383` (fight-rule serialization), `df_fight.cpp:232-270,1422,1869-1870` (parse/latch/export), `src/netplay/replay.cpp:151,251,1456-1459,1479-1505` and `replay.h:52-53` (record/read/check/reconstruct per-match rules), and `src/netplay/netplay_core.cpp:990-1089` (compatibility rejection). Current peer HELLO checks build/seed/flags, not a negotiated match-rules word (`netplay_core.cpp:109-127,627-630,1084-1088`). Proposal: gate enabled skipping on a new lobby capability and updated simulation build/code compatibility identity; distribute one authoritative flag to both players before each fight. If retaining cross-build compatibility, add explicit peer verification of that per-match flag before releasing the fight, including same-session rematches, or disable the option. A player's local preference must never change only one PC's rule. Extend replay rules/format compatibility explicitly so an old reader cannot silently ignore enabled skipping; an old replay defaults to the old rule.

## 2. Even frame pacing on VRR without Special K

### Evidence and likely cause

Goal: steady approximately **16.7 ms** presentation intervals on a VRR display, with input delay no worse than the current build. Supplied observations are alternating approximately 14/19 ms with our pacing, flat intervals with an external 59.9 limiter, game-thread stalls on approximately 0.5% of frames, median game part approximately 2.5 ms and GPU approximately 6% busy. Reproduce them first; their measurement point, display mode, driver limiter and VRR engagement are not known here. Keep the existing nominal 59.94 Hz (`60000/1001`, period approximately 16.6833 ms); 59.9 is a diagnostic comparison, not a reason to silently change simulation speed to 59.9 or 60.

**Likely cause (inference):** a steady game-release tick does not imply steady presents. With early present, `P[n] = release[n] + game[n] + translation/renderer[n]`; variability in that work becomes interval jitter, including short/long pairs. Timer wake jitter, renderer handoff/backpressure and late-path phase resets can add to it. An external limiter smoothing the output supports a presentation-cadence hypothesis; it does not prove a particular timer defect, GPU bottleneck or single root cause. The rare game-thread tail and regular 14/19 alternation may be separate problems.

### Measure first, especially the 0.5% game-thread tail

1. On the player's visible, focused VRR setup, record the exact present mode, display refresh/VRR range, fullscreen/borderless/window mode, driver settings, frame slots and power settings. Disable external limiters/Special K for baseline; compare external 59.9 limiting only as a separate controlled run. Interleave repeated before/after runs of the same fight, stage, resolution and input. Separate loading/cold shaders from warm fighting. Use at least 10 minutes per steady configuration (~36,000 frames, ~180 tail events if the rate holds), not a 1,000-frame average. Repeat quiet and realistically loaded runs.
2. Correlate one QPC timebase and flip sequence across existing `PS3_FRAMELOG`, `PS3_LATENCY_LOG` (E/R/B/F/X/K/P), `PS3_GAME_THREAD_LOG`, rollback counters and a narrow `PS3_SCHED_TRACE` window. Existing analysis: `tools/game_thread_times.py:29-49,60-70`; definitions and profiler switches: `docs/RENDER_PERF.md:1197-1225,1602-1622`. Add a bounded host trace ring to retain events around a late frame, rather than synchronous per-frame disk flushing that creates its own tail.
3. **Classify each slow game part before optimizing code:** release -> actual main-thread wake, wake -> game work, SPURS kick/wait/helper work, draw-request thread/cond/lwmutex waits, net input/barrier waits, rollback snapshots/re-simulation, flip request. Compare wall time with per-thread CPU/cycles; cycles-to-time estimates need clock context. A large wall-minus-CPU tail suggests waiting/preemption; increased CPU requires a busy-stack profile, not a sleep fix. Correlate ready-to-run scheduling/CPU migration, clocks, hard faults, allocations/file I/O and DPC/ISR activity with a maintainer-local OS trace if needed. Do not infer a GPU wait from utilization alone.
4. Report p50/p95/p99/**p99.5/p99.9**, worst, counts above 17.5/20/33.4 ms, consecutive stalls, and the event timelines of worst frames. At a 0.5% rate p99 can hide the whole issue. Median 2.5 ms leaves ordinary-frame headroom but says little about the tail. GPU 6% busy suggests spare average capacity, not proof against an individual fence/present stall. Inspect `gpu_us`, allocator/fence waits, renderer queue/sync waits and Present blocking on those same frames. Keep network/time-sync drops separate from local scheduling stalls.

### Proposed exact pacing change

Implement as a host-only runtime patch after the current series, with a comparison switch; keep fixed-refresh display lock and unsupported backends on their existing paths until measured. Start with explicit VRR/tearing opt-in, not unreliable automatic VRR detection.

1. **Absolute schedule on QPC.** Factor a testable pacer used by `boot_main.cpp` and `rsx_live_draw.c`. Define presentation slots `P[n] = epoch + n * QPF * 1001 / 60000`, using integer quotient/remainder accumulation to avoid drift. The epoch and slot number survive early event wakes; never set a normal deadline to `now + period` each frame. Carry an immutable `{generation, flip_sequence, slot, present_target_qpc}` with the frame through `RQ_PRESENT`; do not read the mutable global next-tick target later on the renderer and accidentally assign another frame's deadline.
2. **Reuse high-resolution timers correctly.** Add `wait_until_qpc(deadline, wake_events)` to the existing host wait support. Re-read QPC after every FIFO/event/spurious wake; compute remaining time against the same deadline. On Windows reuse/create a per-thread `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` handle, arm a one-shot negative relative 100 ns due time from that remaining duration, and finish with a small bounded spin only if measurements justify it (begin with a tunable <=200 microseconds). A positive QPC value is not a Windows absolute timer date. Preserve FIFO kicks, shutdown, fallback timer and laptop power behavior; record wake lateness and fallback use. No periodic millisecond sleep or unbounded busy loop.
3. **Target the actual Present call.** In `rsx_live_draw.c::ld_present_body`, complete resource preparation/GPU submission as early as necessary, then wait to the assigned target immediately before the real DXGI Present call. Preserve legal tearing/sync flags and swap-chain maximum latency; do not add a second external limiter, GPU-completion fence wait or extra buffered frame. The renderer owns this deadline in the overlap path; the inline path must not sleep through the ticker's message/FIFO responsibilities. Audit `ld_xo_sync`, ownership locks and the recorder ring before enabling: a long wait while owning resources needed by the next walk would serialize the pipeline. Instrument that wait explicitly and coordinate next release; do not remove synchronization or snapshot safety to hide it.
4. **Move release/input sampling with the target.** Merely holding an already simulated picture until `P[n]` can add input delay. Release the game's frame and retain its main-thread late input sample at `R[n] = P[n] - B`, where `B` is the measured release-to-submit-ready budget plus a small calibrated guard, bounded below one period. Estimate from a rolling high percentile, increase promptly on genuine local misses and reduce slowly; freeze the estimate for controlled A/B runs. Do not budget network/time-sync holds as ordinary render cost. Coordinate flip completion with that release schedule while preserving one ordered simulation frame per release and the existing handlers/barriers. Keep the previous frame presenting concurrently where resource safety permits. No input-delay frame setting, guest dt, netplay frame numbering or rollback horizon changes.
5. **Define misses and recovery.** If a picture is late, present it once when ready; do not wait another full period as the old pre-0059 behavior did. Reserve a subsequent presentation slot at least one nominal period after the late actual present (advance/rebase host target slots explicitly); do not emit an immediate short catch-up interval or a burst of simulated frames. Slot skips are host deadline bookkeeping, not dropped guest simulation frames. Reset the epoch on resume/occlusion/mode changes and invalidate queued old-generation targets. Honor `cellGcm_skip_ticks()` exactly once for rollback time sync and retain its distinction from a genuinely slow frame; never compensate away an intentional skip. Document this recovery alongside the existing late-flip grace.

**Latency is a release gate, not an assumption.** Flat pacing cannot be proved latency-neutral from source: the current early path sometimes displays sooner, and a larger safety budget samples earlier. Start with the smallest stable budget, compare random-phase pad E/R -> first reacting presented frame and actual visible reaction at p50/p95/tail against baseline, at unchanged netplay input delay. If there is a repeatable regression, revise release phase/budget or keep the new mode opt-in; do not claim the goal is met because the FPS graph is flat. Existing `tools/latency_test.py:153-308` is useful for event correlation, but its DWM/+0.5 ms display estimate and minimized default (`:400`) do not prove visible VRR latency. Use a focused visible run and independent display/latency measurement in the maintainer's environment.

### Present-interval instrumentation to add

Extend `rsx_live_draw.c::ld_pf_frame_log` and the real Present call site (patch 0005 anchors above; the effective function is moved by later patches), plus `tools/perf_compare.py`/a parser test. Keep existing CSV columns for compatibility and append:

- Flip/slot/generation identity; scheduled release/present QPC, actual release, submit-ready QPC, present-call-entry QPC and present-return QPC, HRESULT and DXGI present count. Mark successful, occluded, resize and device-error cases separately.
- **`present_interval_us = (entry[n] - entry[n-1]) * 1e6 / QPF`**, measured immediately around the actual DXGI call, not overlay preparation, ticker firing or async enqueue. Mark first frame and mode/generation discontinuities invalid. Also record return interval, call duration, target lateness, timer-wake error, target-wait time, swap-chain wait, renderer-sync/ring wait and GPU wait separately.
- Keep the preexisting `dt_us` meaning: patch 0005 logs between `present_begin` values, which can include work before actual Present. Existing P is a return event. Neither alone proves call-entry cadence, GPU readiness or scanout cadence. Buffer trace output off the critical path and measure its overhead with logging on/off.

Add a distribution/time-series report: median, p95/p99/p99.9, standard deviation, alternating-neighbor correlation and count outside an initially proposed +/-0.5 ms of 16.6833 ms for ready/on-time steady frames. Report **all** misses, stalls and intentional time-sync skips separately as well; do not hide them through the steady subset. Join to independent displayed-frame timing/VRR evidence, where supported, to detect DWM/driver queuing, duplicates and dropped presents. Present return is not a photon timestamp. Adjust the numeric tolerance only with measured platform limits and record the reason.

**Determinism risk:** host timing changes should alter when frames run and display, not what they compute. Tick/handler ordering, shared-buffer lifetime, time-sync skips and accidental input resampling are the main hazards. Retain the existing guest-buffer handover wait (`docs/RENDER_PERF.md:96-110`); the game rewrites commands/data and cannot safely be let ahead merely because a present moved to another thread. Any proposed change to those ownership barriers requires separate proof.

**Unknown until build/game runs:** the player's true bottleneck and VRR presentation path; actual timer wake error; whether renderer ownership permits the proposed wait without starving translation; a stable budget that also meets the input-latency gate; the source of the rare tail; behavior across drivers/displays/backends. The design is a testable candidate, not a verified performance result. If either latency or pair determinism fails, 1.2.0 must not advertise this pacing goal as achieved.
